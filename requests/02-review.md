## Correctness finding

**A failed diff can look like a clean conflict check.** When untracked local files exist, `checkConflicts` asks Git which paths changed upstream and compares those names with the untracked paths. It consumes stdout even if Git failed. Empty output then clears this part of the check and sync can proceed. The same query uses the runner's default trimming. A space at the start of the first filename disappears before the comparison. Follow the pattern in `changedPaths` by checking the exit code and requesting untrimmed output for the NUL-delimited list. Cover a failed diff and a first filename with a leading space. Both observations come from source inspection and still need runtime verification. [Conflict check](../lib/sync.js#L345) · [Checked path query](../lib/sync.js#L308) · [Runner output](../lib/git.js#L116)

## Refactoring opportunities

1. **Build a reusable Git query module around the existing runner.** `makeGit` already encapsulates process lifetime, timeouts, and noninteractive execution. Status parsing, local changes, changed paths, and Git version parsing belong together and already have consumers in sync, contribution, and Check git. Keep the injected `run` argument so callers retain control of logging and tests. Keep managed-clone switching, locking, user-facing messages, and the decision to rebase in the extension workflows. Extract an external package once another project can exercise its API. [Runner](../lib/git.js#L21) · [Repository queries](../lib/sync.js#L260) · [Check git](../lib/gitCheck.js#L5)
2. **Move filesystem operations to the modules that own those responsibilities.** Authoring, sharing, and partial-copy sync all import `removeTree` from Git sync. Conversely, contribution imports `caseInsensitive` from partial-copy sync to protect ignored files during push cleanup. These two functions can live in a filesystem module. File locking has a similar boundary. Updating the seen record needs the lock and heartbeat, while repository operations also need stale Git index-lock cleanup under that lock. Keep the latter in a repository-specific wrapper. [Authoring](../lib/authoring.js#L9) · [Push cleanup](../lib/contribute.js#L205) · [Lock](../lib/sync.js#L122) · [Seen record](../lib/updates.js#L346)
3. **Give both push workflows one preparation step.** After their respective remote checks, both inspect local changes, translate a status failure, return early when there is nothing to push, and commit pending files. Extract that sequence under the existing lock. An ahead-only branch must continue directly to push. This gives a future change to staging behavior one place to land while keeping upstream rebase and new-branch cleanup explicit in their callers. [Push upstream](../lib/contribute.js#L51) · [Push to a branch](../lib/contribute.js#L127)
4. **Isolate the ordinary-file decision in partial-copy sync.** For a selected file, the source, copy, and recorded hashes determine the action and the next recorded hash. Express that decision in a pure function with named inputs and a table of cases, including an absent file and an unknown baseline. Leave scanning, case-only renames and their rescan, unreadable paths, and generated MCP content with the existing filesystem workflow. Take this up when the sync rules next change, and retain the filesystem tests alongside the decision tests. [Sync workflow](../lib/materialize.js#L421)

## Readability improvements

- **Make the workspace and folder settings reads easy to compare.** The adjacent `projectList` and `projectRepositories` functions repeat the same traversal and the subtle choice of `workspaceValue` versus `workspaceFolderValue`. Extract a small reader that returns the raw values for a setting in their current order. Each caller can then show just its own parsing and ID normalization. Keep writes explicit since adding an item targets one chosen folder and removing it checks every scope. This is the smallest readability change I would take first. [Readers](../extension.js#L283) · [Add](../extension.js#L1872) · [Remove](../extension.js#L1919)
- **Move repository subtree assembly into the existing tree model.** To discover what a repository row contains, a reader currently has to follow `PluginTree.getChildren` through conflict and change groups, repository-prefixed update IDs, plugin rows, a fallback error row, and finally `buildRepoNode`. Move the per-repository assembly next to the existing node builders. The provider can read window state and publish decorations. The model can then test row order, prefixed marks, and the empty-repository error case with plain objects. [Provider](../extension.js#L1719) · [Plugin rows](../lib/treeModel.js#L41) · [Repository row](../lib/treeModel.js#L296)
- **Name the two sources of selection.** In `effective`, the hard part is understanding why excluding a child in user settings still allows the project to enable it. Renaming `u` and `r` to `userIncluded` and `projectIncluded` makes that rule visible at the union and explains what feeds `fromProject`. In `toggle`, use `pluginName` for `P` so the branches that collapse individual child selections into a whole-plugin setting read directly. Both changes can stay local. [Effective selection](../lib/selection.js#L11) · [Toggle](../lib/selection.js#L58)
